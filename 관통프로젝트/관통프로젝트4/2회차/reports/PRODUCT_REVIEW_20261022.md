# FinVOC Korea 내용·데이터·디자인 점검

점검일: 2026-10-22. 대상: 현재 로컬 앱, Python 구현, 프로젝트 명세, 실제 정제 데이터와 검증 기록.
검토 중 외부 HTTP·GMS 호출은 하지 않았다. 이번 산출물은 진단 보고서와 탐색 검사 기록이며 앱 수정 완료 보고서가 아니다.

## 판단

공식 공시와 사례의 출처를 보존하고 서로 다른 모집단을 섞지 않는 기반은 갖추었다.
현재 구현은 **보험 민원 통계 분석과 공개 사례 원문 탐색 단계**다. 명세의 의미 검색·LLM 생성·사례 비교·개선 보고서·독립 평가가 아직 남아 있다.
더 많은 회사를 추가하는 것보다 **회사 표시 일치, 범위 밖 검색 처리, 유형별 변화 분석, 검증된 RAG**를 먼저 완성하는 편이 포트폴리오의 기술·업무 설득력을 높인다.

## 1. 즉시 수정할 실제 결함

### P1 — 화면 이동 후 회사·기간·검색 조건 소실 및 회사 표시 불일치

- 실제 브라우저: 삼성화재 선택 → 사례 탐색 → 업무 개요 복귀 시, 선택창은 AIG손해보험인데 본문은 하나손해보험·75건으로 표시되는 현상을 재현했다.
- 새로고침 후에는 선택창과 본문이 하나손해보험으로 일치했다. 이후 같은 메뉴 이동에서 불일치가 다시 발생했다. 최초 로딩 중 한 번의 화면만 보고 결론 내린 것이 아니다.
- 별도의 AppTest: 삼성화재·2026Q1 → 사례 탐색 → 업무 개요에서 하나손해보험·2026Q2로 초기화됐다.
- 검색창도 ‘백내장 입원’으로 검색한 뒤 다른 화면을 다녀오면 빈 입력창과 기존 검색 결과가 함께 남았다.
- 17개 손해보험사를 직접 하나씩 선택한 AppTest에서는 민원 합계가 모두 정제 데이터와 일치했다. 원본 숫자 집계 오류와 메뉴 이동·화면 상태 오류를 구분해야 한다.

관련 위치: `app.py:44`, `src/ui/views.py:22`, `src/ui/views.py:180`.
입력 위젯 값과 지속해야 하는 업무 상태를 분리하고 회사·기간·검색 조건을 하나의 분석 맥락으로 유지할 필요가 있다.
원인은 상태 관리 지점으로 좁혔으며 정확한 브라우저/위젯 동기화 원인은 추가 수정·검증이 필요하다.

**완료 기준:** 회사 선택 → 사례 탐색/자료 관리 → 복귀 및 업권 전환을 해도 의도한 상태를 유지한다.
선택창·본문 회사명·출처·모든 KPI가 항상 같은 회사와 기간을 가리키는지 실제 브라우저에서도 검사한다.

증거: [재현 화면](evidence/review_20261022/reproduced-selection-mismatch.png),
`ux_review_flow_probes.json`.

### P1 — 범위 밖 질문에도 무관한 사례를 ‘근거’처럼 노출

실제 질문 **‘해외주식 양도소득세 신고 방법’**에 자동차보험 휴업손해 사례가 1위로 표시됐고 총 5개 후보가 나왔다.
‘대출 금리인하요구권 신청’, ‘예금 인출이 안돼요’도 보험 사례를 반환했다.
첫 질문은 실제 브라우저에서도 같은 결과를 확인했다. 테스트용 영문 무작위 문자열만 0건이 되는 것으로는 부적합 질문을 처리했다고 볼 수 없다.

원문 검색은 현재 문자 2·3·4-gram TF-IDF이며, `src/analysis/case_search.py:44`에서 점수가 0보다 크기만 하면 후보에 넣는다.
인용 검사(`case_search.py:65`)는 해당 문서에 문구가 실제 존재하는지 확인하지만 질문 관련성이나 주장과 근거의 의미 일치는 판단하지 않는다.
이는 현재 생성 답변이 환각했다는 뜻은 아니다. 생성은 연결 전이다. 그러나 이 후보를 그대로 LLM 근거로 넣으면 오답 위험이 생긴다.

**개선:** 지원 범위 안내 → 분야/서비스 판단 → 검색 → 관련도 검증 → 근거 부족 보류의 순서를 둔다.
관련도 문턱을 임의 숫자로 고정하지 말고, 검수한 지원/미지원 질문과 별도의 검증 집합으로 결정한다.
필터로 서비스군을 줄인 경우 점수 분포도 달라질 수 있다. 원문 후보 단계에는 ‘검색 후보’라고 표시하고 검증 전 ‘근거 1’ 표현은 피한다.

**완료 기준:** 보험 밖 질문에는 지원 범위를 알리고 답변을 보류한다. 보험 질문과 일반 금융 질문,
동의어·오타·무관 질문을 포함한 독립 정답셋으로 검색 적중과 잘못된 후보 노출을 함께 측정한다.

증거: [실제 검색 화면](evidence/review_20261022/out-of-scope-search.png),
`ux_data_review_probes.json`, `ux_review_flow_probes.json`.

## 2. 내용·분석 기능 개선

### P1 — 현재 건수 중심에서 변화 원인 검토 중심으로

현재 `snapshot()`의 상위 유형은 건수 내림차순이다. 우선 검토 카드도 이 순서를 그대로 사용한다.
예를 들어 삼성화재 2026Q2 실제 공시는 다음과 같다.

|유형|2026Q1|2026Q2|변화|
|---|---:|---:|---:|
|보상(보험금)|1,801|1,597|-204|
|유지관리|156|196|+40|
|보험모집|136|129|-7|
|기타|106|104|-2|

가장 많은 유형은 보상이지만, 증가한 유형은 유지관리다. 현재 화면은 이 차이를 충분히 드러내지 못한다.

**개선:** ‘건수가 많은 유형’과 ‘전분기 대비 증가한 유형’을 구분한다. 건수·비중·증감 건수·증감률을 함께 표시한다.
작은 전기 분모 때문에 증감률만 커진 항목은 전기 건수를 같이 보여주고, 0건 분모는 증가율 대신 신규 발생으로 표시한다.
이 지표는 내부 검토 순서이며 피해 심각도·법적 책임·서비스 품질 등급이 아니다.

**완료 기준:** 위 표를 실제 데이터에서 재계산하고 유지관리 +40건이 첫 화면 검토 대상으로 드러난다.

### P1 — 명세의 AI 기능과 평가 완성

현재 한국어 의미 임베딩·ChromaDB·LangGraph/GMS 답변 생성은 구현·검증 전이며,
사례 두 개 비교와 근거 기반 개선 검토 보고서도 없다. 기존 다른 프로젝트의 GMS 실검증 결과를 FinVOC의 성과로 사용할 수 없다.

**개선 순서:** 지원 범위/보류 처리 → 문자 검색 기준선 평가 → 의미/하이브리드 검색 → 근거 생성·인용 검증 → 사례 비교/보고서.
독립 30문항 이상을 제안하되, 질문만 작성한 것을 정답셋 완성으로 보지 않는다. 관련 사례 ID·관련성 수준·원문 근거·검수 상태가 필요하다.
검색은 Hit@k/Recall@k 등, 생성은 주장-인용 의미 일치·없는 인용·근거 부족 보류·사례 혼합·응답 시간을 별도로 평가한다.
개발에 쓴 질문과 최종 평가 질문을 분리한다. 사람 검수 전 지표는 검수 완료로 쓰지 않는다.

### P2 — 통계 유형에서 관련 사례로 가는 연결을 정교화

현재 ‘보상(보험금)/지급’ 카드가 모두 진료비 영수증 추가 서류 질문으로 이어진다.
생명보험 지급이나 자동차보험 보상에도 같은 질문이 쓰여, 회사·상품 상황과 어긋날 수 있다.

**개선:** 업권과 사용자가 선택한 상품/서비스를 반영한 검토 주제를 제안한다.
공시가 ‘보상’이라는 대분류만 제공하면 세부 원인을 단정하지 않고 서비스 선택을 받는다.
익명 사례는 계속 ‘업계 관련 사례’로 유지하며 회사별 실제 사건으로 배정하지 않는다.

## 3. 데이터 개선

### P1/P2 — 자료 범위와 업무 주장 맞추기

실제 파일을 모두 파싱해 확인한 현재 범위:

- 회사는 손해보험 17개·생명보험 1개. 전 업권이 고르게 확보된 것은 아니다.
- 회사 17개는 2개 분기, 하나손해보험 1개만 3개 분기. 장기 추세·계절성·지속 반복을 확정하기 어렵다.
- 사례 70개 중 서비스 라벨은 손해보험 25, 자동차보험 20, 실손보험 10, 질병·상해·간병보험 9,
  생명보험 3, 보험 일반 3이다. 이 분포는 수집된 공개 문서의 구성이지 전체 민원 발생 분포가 아니다.
- 회사명·결정일·분리된 양측 주장 필드는 70개 모두 미확인이다. 판단/처리 내용은 `resolution_text`에
  통합 보존되어 있으며, 빈 개별 필드가 ‘원문에 판단이 없다’는 뜻은 아니다.
- 55개 문서의 게시일이 2026-01-09로 같다. 이를 사건 발생일이나 최근 분쟁일로 해석할 수 없다.
- 제목 중복 억제로 69개가 검색 대상이다. 제목 동일성만으로 사건 동일성이 확인되는 것은 아니므로 문서 계보 검토가 필요하다.
- 새 15개 손해보험사 상품 환산값의 상세 분모가 미확인이다. 현재 비교 차트 차단은 유지해야 한다.

**개선:** 첫 화면에 ‘손보 17·생보 1 / 공통 2026Q2 / 공개 사례 70’를 표시한다.
주요 2~3개 회사의 동일 기준 과거 4~8분기를 먼저 보강하고 변경된 공시기준은 표시한다.
생보를 더 다루려면 생보 회사 공시와 관련 사례 범위를 함께 보강한다.
‘기업의 실제 대응 효과’까지 설명하려면 기업명과 조치·시점·후속 결과가 확인되는 별도 원문이 필요하다.
현재 자료만으로 기업별 개선 조치가 성공했다고 주장하지 않는다.

### P2 — 자료의 시점과 갱신 이력 분리

수집 캐시는 URL 기준으로 영구 재사용하며 기존 URL에 새 분기가 올라와도 자동 확인하지 않는다.
보고서의 실행 시각과 원문의 실제 수집 시각도 다르므로 ‘자료 확인’ 날짜 하나만 보여주면 최신성을 오해할 수 있다.

**개선:** 공시 대상기간 / 원문 수집일 / 최근 원격 변경 확인일 / 로컬 검증 실행일을 구분한다.
새 버전 확인 기능과 불변 스냅샷 보관을 분리한다. 갱신은 기존 원문을 덮어쓰지 않고 새 영수증으로 추가한다.
정책 변경도 확인하고, 원격 갱신 실패를 로컬 캐시 검증 성공과 구분한다.

## 4. 디자인·사용성 개선

### P2 — 첫 화면에 업무 결론과 다음 행동 배치

현재 1268×976 데스크톱 화면에서 로고·메뉴·소개·메타·필터·KPI가 세로 공간을 많이 차지한다.
‘우선 살펴볼 민원 유형’ 카드가 첫 화면 아래로 밀려 담당자의 다음 행동이 즉시 보이지 않는다.

**제안 배치:** 간결한 제목/자료 기준 → 회사·기간 필터 → ‘전분기 대비 증가한 유형’ 요약과 사례 검토 버튼 → 핵심 KPI → 분포/추이 → 원문·상세 기준.
네이비·청록·화이트 톤은 유지하고, 장식보다 정보 우선순위를 조정한다. 통계적 변화는 계산 사실로,
원인이나 조치는 검토 가설로 표시한다.

### P2 — 중요한 안내 가독성 및 출처 추적

기준일·업권·비교 제한은 작은 회색 글씨와 긴 문장으로 표시되어 지나치기 쉽다.
중요한 제한은 짧은 상태 배지와 읽기 쉬운 본문 크기로 올리고 세부 설명은 펼침 영역에 둔다.
사례 긴 제목과 장문 처리결과는 ‘쟁점 / 중요 조건 / 처리결과 / 원문 문단’ 구조로 읽을 수 있게 한다.
요약을 생성한다면 근거 문단을 바로 펼칠 수 있도록 연결한다.
데이터 검증 247/247은 합계·형식·출처 대조 등 내부 검사 수이며 검색 정확도나 AI 정답률이 아니다.
업무 화면에서는 자료 범위를, 평가 화면에서는 검사 종류와 미검증 항목을 구분해서 보여주는 편이 낫다.

**완료 기준:** 첫 화면에서 기준과 다음 검토 행동이 읽히고, 1366×768 등 더 낮은 높이에서도 주요 조작부가 접근 가능하다.
이번에는 1268×976 데스크톱에서 확인했으며 실제 모바일 기기 검증을 했다고 기록하지 않는다.

회사를 더 늘리거나 분류 모델 종류를 추가하는 것은 위 핵심 흐름을 검증한 뒤 진행한다.
모델 학습은 사람이 검수한 라벨과 학습/평가 분리를 먼저 확보한다.

## 점검의 범위와 산출물

기존 pytest 30개 통과 기록은 이전 구현 검사 기록이다. 이번 점검은 별도의 오프라인 탐색 검사이며,
그 30개로 검증되지 않았던 메뉴 이동과 범위 밖 질문 문제를 찾아냈다.
